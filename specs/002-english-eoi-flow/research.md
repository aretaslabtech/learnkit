# Research: Flujo end-to-end de inglés (clase EOI — vocabulario)

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Todos los desconocidos del Technical Context quedan resueltos con las decisiones siguientes. No quedan `NEEDS CLARIFICATION` abiertos.

## 1. Invocación del provider de transcripción por defecto (whisper.cpp)

- **Decision**: invocar el binario `whisper.cpp` (o su CLI `whisper-cli`/`main`) como subproceso, pasándole el fichero de audio y recogiendo su salida (JSON si el binario lo soporta, o su formato de texto/SRT parseado a nuestro esquema canónico), detrás de un trait `TranscriptionProvider`.
- **Rationale**: es exactamente el patrón que `docs/14-transcription.md §2` fija como decisión de arquitectura ("fácil de invocar desde un binario Rust mediante adapter/command provider"; "evita hacer de Python una dependencia obligatoria"). No añade bindings FFI ni una dependencia de compilación pesada al CLI.
- **Alternatives considered**: bindings Rust directos (`whisper-rs`) — más rápido en tiempo de ejecución pero acopla la compilación del CLI a la disponibilidad de toolchains C++/modelos GGUF en cada plataforma de build, lo que complica la distribución del binario; se descarta para V1 y queda como optimización futura si el subproceso resulta insuficiente en el benchmark de `docs/14 §6`.

## 2. Sugerencia de vocabulario objetivo (FR-012/FR-012b)

- **Decision**: la "sugerencia automática" no se implementa como un motor de NLP embebido en el binario Rust. El CLI expone el material de la sesión (notas + transcript) en un formato legible por el agente (`learnkit session show --json`, ya con los segmentos/texto), y una Skill de agente (`learnkit-language`, análoga a las ya previstas en `docs/09-agent-integration.md §7`) es la que analiza el texto y propone candidatos de vocabulario a la persona en la conversación. El CLI solo expone el comando para **persistir** una entrada de vocabulario ya confirmada (`learnkit learn vocabulary add ...`), con su trazabilidad de origen.
- **Rationale**: mantiene el núcleo determinista y sin dependencias de NLP/ML (coherente con "no perseguir una métrica académica perfecta" de `docs/14 §6` y con el patrón ya existente de "semantic check asistido por agente" de `docs/04-workflow-guards.md §9`, que reserva el análisis semántico a un check separado, nunca sustituyendo un check determinista). Evita añadir una dependencia de diccionario de frecuencias/phrasal-verbs que habría que mantener y que un LLM ya hace mejor de forma conversacional. El requisito de la spec ("el sistema sugiere, el usuario confirma") se sigue cumpliendo desde la perspectiva del usuario, que interactúa con LearnKit a través del agente.
- **Alternatives considered**: heurística determinista en Rust (lista de palabras frecuentes + diccionario estático de phrasal verbs + umbral de frecuencia) — viable y 100% offline, pero de calidad mucho menor que un agente conversacional y con mantenimiento propio de datos lingüísticos; se descarta como mecanismo principal. Se puede añadir en el futuro como fallback determinista si se usa LearnKit sin ningún agente delante, pero no es requisito de esta feature (la spec no exige funcionar sin agente para este paso).
- **Impacto en el plan**: esta decisión es la de mayor impacto de todo el research y se señala explícitamente al usuario en el informe de finalización de `/speckit-plan`, por si prefiere forzar una heurística determinista en su lugar.

## 3. Provider de voz por defecto (FR-017b)

- **Decision (revisada 2026-09-27, tras uso real)**: el default pasa de `Piper` a un `RestVoiceProvider` que llama al servicio TTS ya desplegado por el usuario (`travisvn/openai-edge-tts`, envoltorio REST de `edge-tts`, compatible con el endpoint `POST /v1/audio/speech` estilo OpenAI), en `https://tts.davidpalazon.net/v1/audio/speech`, voz `en-GB-SoniaNeural` por defecto. Sigue detrás del mismo trait `VoiceProvider`, sin cambiar la forma `request -> AssetDraft`. La credencial se lee de la variable de entorno `TTS_API_KEY`; nunca se hardcodea ni se persiste en el repositorio.
- **Rationale de la revisión**: la decisión original (Piper local) asumía que el binario y el modelo `.onnx` estarían instalados en la máquina de desarrollo; en la práctica no lo estaban, y el usuario ya tiene un servicio REST propio, desplegado y verificado, que cubre el mismo caso de uso sin esa fricción de instalación. `PiperVoiceProvider` se conserva en el código (no se borra) como provider alternativo detrás del mismo trait, para quien prefiera un flujo 100% offline.
- **Alternatives considered (decisión original, 2026-09-XX)**: usar `Piper` (TTS neuronal local, offline) como default — ver más abajo. Se descarta como *default* por la razón anterior, pero sigue disponible.
- **Alternatives considered (histórico)**: proveedor cloud (OpenAI TTS, Azure, ElevenLabs) — mejor calidad de voz pero rompe el funcionamiento offline por defecto y añade coste/latencia de red; esta es exactamente la alternativa que ahora se adopta como default, vía el wrapper `openai-edge-tts` ya operado por el usuario.

## 4. Búsqueda de imágenes en Wikimedia Commons (FR-017c/d/e)

- **Decision**: usar la API pública de MediaWiki de Wikimedia Commons (`commons.wikimedia.org/w/api.php`) con `action=query&generator=search&prop=imageinfo&iiprop=url|extmetadata`, filtrando por licencias reutilizables con atribución (Creative Commons) leídas de `extmetadata.LicenseShortName`/`LicenseUrl`, vía `reqwest` + `serde_json`. Sin API key (la API de búsqueda pública no la requiere para este volumen de uso).
- **Rationale**: es la única vía oficial soportada sin scraping ni credenciales, coherente con el principio de interoperabilidad "sin scraping cuando exista una vía estándar" ya aplicado a TAO/QTI en `docs/13-decisions.md` ADR-013.
- **Alternatives considered**: Wikimedia Commons SDK/cliente de terceros — añade una dependencia extra por una superficie de API pequeña; se prefiere una llamada HTTP directa con `reqwest`, ya previsto como dependencia opcional del proyecto (`docs/02-architecture.md §4`, "HTTP providers: `reqwest` cuando sea necesario").
- **Adición (revisada 2026-09-27, tras uso real)**: `resolve_image` (`crates/learnkit-media/src/resolve.rs`) trataba cualquier fallo de `image_provider.search()` — incluido un fallo de red transitorio o el timeout de 8s del cliente — exactamente igual que "no se encontró ninguna imagen con licencia compatible" (FR-017e), sin reintento. Con 153 llamadas HTTP secuenciales reales, esto causaba que un subconjunto distinto y aparentemente aleatorio de palabras quedara `pending_image` en cada ejecución de `cards build` — no porque esas palabras fueran intrínsecamente difíciles de ilustrar, sino por intermitencia de red/API. **Decisión añadida**: `resolve_image` DEBE reintentar la búsqueda un número acotado de veces (con una breve espera entre intentos) antes de tratar un fallo del proveedor como definitivo; un resultado `Ok([])` (búsqueda que respondió pero no encontró candidatos con licencia válida) sigue considerándose definitivo de inmediato, sin reintento, porque no es un fallo transitorio.

## 5. Generación del `.apkg` (FR-018/019/020)

- **Decision**: generar el `.apkg` directamente en Rust: escribir la base `collection.anki2` (SQLite, esquema de notas/cards/decks de Anki) con `rusqlite`, empaquetar junto al `media`/`media.json` con el crate `zip`. GUIDs deterministas derivados de `sha256(card_id)` truncado al rango esperado por Anki.
- **Rationale**: `docs/07-anki-media.md §10` exige un spike técnico obligatorio antes de comprometerse a esta vía; esta decisión fija la vía a probar primero (Rust puro) porque evita añadir un runtime externo (p.ej. Python/`genanki`) como dependencia del binario distribuible, coherente con ADR-001. Si el spike (primera tarea de la historia US5 en `tasks.md`) revela que el esquema SQLite de Anki es más frágil de lo esperado, la spec de arquitectura ya prevé el fallback.
- **Alternatives considered**: invocar un helper externo aislado solo como renderer (p.ej. un binario Python con `genanki`) — expresamente permitido como fallback temporal por `docs/07-anki-media.md §10` si el spike en Rust falla; se documenta aquí como plan B, no como decisión primaria.

## 6. Modelo de workflow/DAG y guards (US1)

- **Decision**: representar las fases (`inventory`, `analyse`, `learn`, `vocabulary`, `cards`, `anki`, `assessment`) como un mapa `HashMap<PhaseId, Vec<PhaseId>>` de dependencias declaradas en `.learnkit/workflow.toml` (ya creado por `learnkit init` en la feature 001), con orden topológico simple (sin librería de grafos: el pipeline V1 es pequeño y lineal con alguna rama, ver `docs/04-workflow-guards.md §2-3`). Cada fase escribe un manifest JSON con fingerprints de entrada/salida; el estado (`not_started`/`dirty`/`valid`/`blocked`/`failed`) se recalcula en cada `run`/`validate`/`status`, nunca se lee como autoridad de un manifest cacheado.
- **Rationale**: usar una dependencia de grafos (`petgraph`) para un DAG de ~7 nodos fijos sería sobre-ingeniería; una función de orden topológico de pocas líneas es suficiente y más fácil de auditar (coherente con "Simplicity"/YAGNI implícito en la constitución).
- **Alternatives considered**: `petgraph` — descartado por desproporcionado para el tamaño real del problema en V1.

## 6b. Sesión activa (FR-003b, añadido post-implementación tras feedback del usuario)

- **Decision**: guardar la sesión activa en `.learnkit/active-session.json` (`{"session_id": "..."}`), escrita/leída por un módulo nuevo `learnkit-store::active_session`, con escritura atómica igual que el resto del estado del proyecto. `session new` la fija automáticamente; `session use <id>` la fija explícitamente; todos los comandos de esta feature que aceptan `--session` lo hacen ahora opcional y caen a la sesión activa si se omite.
- **Rationale**: el propio usuario señaló el paralelismo con `.specify/feature.json` (que ya usa este mismo repositorio para la feature Spec Kit activa) — un puntero local, no versionado, que evita repetir el identificador en cada comando. Ponerlo en `learnkit-store` (no en `learnkit-workflow`) porque es estado de proyecto, no de dominio del workflow, igual que `learnkit.toml`/`session_paths`.
- **Alternatives considered**: variable de entorno (`LEARNKIT_SESSION`) — descartada como mecanismo principal porque no persiste entre invocaciones de terminal distintas sin que el usuario la exporte él mismo; queda como posible complemento futuro, no como sustituto del puntero en disco.

## 7. Resultados de examen y cierre del ciclo local (US6/US7)

- **Decision**: el examen HTML autocontenido (`docs/08-assessment-games-progress.md §6`) se completa en el navegador y ofrece un botón "descargar resultados" que genera un JSON de intentos; `learnkit attempt import <file>` (ya prevista en `docs/05-cli-spec.md §"learnkit attempt import"`) lo ingiere y lo añade a `attempts.jsonl` de forma append-only. `learnkit progress` agrega ese log en el momento de la consulta.
- **Rationale**: es la única forma de que un examen "funcione localmente sin servidor" (requisito explícito) y aun así alimente el histórico de intentos de LearnKit sin necesitar un backend.
- **Alternatives considered**: servidor local embebido en el CLI para recoger resultados en caliente — añade superficie (puerto, ciclo de vida del proceso) sin necesidad real, ya que el examen es una sesión síncrona corta; se descarta.

Ejecutado `cargo metadata` sobre el workspace completo (5 crates de la feature 001 + 6 nuevos de esta feature, `Cargo.lock` fijado). ## Resultado del spike de Anki (T054, post-implementación)

El spike de `docs/07-anki-media.md §10` se ejecutó: `collection.anki2` se genera con `rusqlite` (esquema legacy versión 11) y se empaqueta en un `.apkg` (ZIP) junto a `media`/ficheros de media, con GUIDs deterministas por `card_id` (`research.md` §5, `learnkit-anki::guid`). Verificado automáticamente: la estructura del ZIP (`collection.anki2`, `media`, ficheros de media numerados), que `collection.anki2` es una base SQLite válida con el esquema esperado, que los conteos de notas/tarjetas coinciden con las `CardDefinition`s exportadas, y que reexportar las mismas tarjetas produce los mismos IDs de nota (sin duplicados al reimportar).

**Verificado manualmente contra Anki Desktop real (2026-09-27)**: el usuario sí tenía Anki Desktop instalado. Se importó un `.apkg` generado por `learnkit export anki` real y las 2 tarjetas aparecieron correctamente en Anki. Primera vuelta: la imagen no se veía — bug real encontrado y corregido (ver más abajo). Tras el arreglo, reimportado y confirmado: **la imagen se ve correctamente**. El spike de `docs/07-anki-media.md §10` queda cerrado con validación real, no solo estructural.

### Bug real encontrado y corregido durante esta validación: descarga de imagen sin `User-Agent`

`resolve_image`'s callback de descarga (`download_image` en `crates/learnkit-cli/src/commands/cards.rs`) usaba `reqwest::blocking::get(url)` sin cabecera `User-Agent`. Los servidores de media de Wikimedia (`upload.wikimedia.org`) rechazan peticiones sin `User-Agent` y devuelven una página de error en texto ("Please set a user-agent and respect our robot policy...") con código 200 — que se guardaba sin validar como si fuera la imagen (el JSON de metadatos del asset era correcto: licencia CC0, autor, URL real; solo el contenido binario era la página de error, de 126 bytes).

**Corrección**: `WikimediaCommonsProvider` ahora expone un método `download()` que reutiliza su propio cliente HTTP (mismo `User-Agent`/timeout que la búsqueda) y **valida que el `Content-Type` de la respuesta empiece por `image/`** antes de aceptar los bytes; si no, se trata como fallo de descarga (la tarjeta queda `pending_image`, nunca se registra un asset corrupto). `crates/learnkit-cli/src/commands/cards.rs` ya no hace su propia petición HTTP desnuda.

**Por qué los 155 tests automatizados no lo detectaron**: los tests de `resolve_image`/`asset` usan providers *fake* inyectados (por diseño, para no depender de red real en CI); nunca ejercitaron la petición HTTP real de descarga. `asset::is_valid()` solo comprueba tamaño ≥16 bytes y coincidencia de hash — una página de error de 126 bytes... en realidad *sí* pasa el umbral de 16 bytes, así que ni siquiera esa comprobación mínima lo habría atrapado; la única forma de detectarlo era validar el `Content-Type` en el momento de la descarga (ya corregido) o decodificar el contenido como imagen real (no implementado, sigue siendo una simplificación documentada). Esto confirma que la validación manual contra el servicio real (research.md, "no verificado automáticamente") no era una formalidad — encontró un bug real que ningún test unitario con fakes podía atrapar.
