# Research: Checklist por fase y fases `analyse`/`consolidate` reales

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Todos los desconocidos del Technical Context quedan resueltos con las decisiones siguientes. No quedan `NEEDS CLARIFICATION` abiertos.

## 1. Modelo de datos del checklist (extender `PhaseManifest` vs. estructura paralela)

- **Decision**: añadir un campo opcional `checklist: Option<Vec<ChecklistItemManifest>>` a `PhaseManifest` (`crates/learnkit-workflow/src/engine.rs`), en vez de sustituir `result: PhaseResult` o crear un tipo de manifest completamente nuevo. Una fase sin checklist (`inventory`, `vocabulary`, `cards`, `anki`, `assessment`) sigue escribiendo `checklist: None` y se comporta exactamente igual que hoy. Una fase con checklist (`analyse`) escribe `checklist: Some(vec![...])`; su `PhaseState` agregado (el que ya consume `recompute_state`) se sigue derivando del conjunto de sub-estados: `Valid` solo si todos los elementos están `Done`, `Blocked` si depende de una fase no válida (como hoy), y un nuevo `PhaseState::NeedsUserInput` cuando al menos un elemento está `PendingUserDecision` y ninguno está `Failed`.
- **Rationale**: reutiliza el mismo mecanismo de fingerprints/invalidación en cascada que ya existe (cada `ChecklistItemManifest` tiene su propio `input_fingerprint`, igual que hoy tiene el manifest de fase completo) en vez de inventar un segundo sistema de invalidación en paralelo. Mantiene compatibilidad binaria con los manifests ya escritos por las fases existentes (campo nuevo opcional, `#[serde(default)]`).
- **Alternatives considered**: un tipo `ChecklistPhaseManifest` completamente separado de `PhaseManifest` — se descarta porque duplicaría toda la lógica de fingerprint/invalidación de `engine.rs` en vez de extenderla, y porque `status`/`recompute_state` tendrían que aprender a leer dos formatos de manifest distintos según la fase.

## 2. Quién redacta el contenido y cómo lo confirma la CLI (FR-005/006, confirmado en `/speckit-clarify`)

- **Decision**: un agente (Codex/Claude) vía una Skill nueva y genérica `learnkit-analyse` (sin instrucciones específicas de idiomas, a diferencia de `learnkit-language`) lee el material de la sesión con `learnkit session show --json` (ya expone notas + segmentos de transcripción activa desde la feature 002, T034) y redacta resumen/mapa mental/páginas. Cada elemento se confirma con un comando CLI dedicado (`learnkit analyse summary set --session <id> --file resumen.md`, `analyse mindmap set ...`, `analyse page add ...`) que valida forma/trazabilidad (que el fichero exista, no esté vacío, y — para huecos rellenados — que declare explícitamente su origen) y solo entonces marca el elemento como `Done` con su fingerprint.
- **Rationale**: mismo patrón exacto que la sugerencia de vocabulario de la feature 002 (`research.md` §2 de esa feature): el core Rust se mantiene determinista y sin dependencia de NLP/generación; el CLI nunca "confía" en que el agente hizo bien su trabajo de redacción — solo valida estructura y trazabilidad, coherente con Principio IV (Hard Guards). Confirmado explícitamente por el usuario en `/speckit-clarify`: **"A, si la idea es usar la potencia del llm que la usa"**.
- **Alternatives considered**: generación determinista en Rust (extracción de frases clave, plantillas fijas) — se descarta por la misma razón que en la feature 002: calidad muy inferior a un agente conversacional real, y el usuario confirmó explícitamente que quiere aprovechar el LLM para esto.

## 3. Cómo se marca y resuelve un elemento "pendiente de decisión del usuario" (FR-007/008)

- **Decision**: cuando el agente no puede redactar un elemento (material insuficiente), lo indica no confirmándolo; el usuario o el propio agente lo marca explícitamente como pendiente con un motivo (`learnkit analyse mindmap flag-pending --session <id> --reason "el material no tiene contenido suficiente para un mapa mental útil"`). Ese estado queda visible en `status` (`PendingUserDecision`, con el motivo). Se resuelve de dos formas simétricas al mecanismo de override ya existente (`docs/04-workflow-guards.md §10`, `--accept semantic-check-<id> --reason`): (a) confirmando el elemento normalmente una vez hay más material (`analyse mindmap set ...`, que limpia el estado pendiente), o (b) omitiéndolo explícitamente y de forma auditada (`learnkit analyse mindmap skip --session <id> --reason "..."`), que dejar de bloquear `consolidate`/fases posteriores para ese elemento sin volver a preguntarlo mientras el material no cambie.
- **Rationale**: no se introduce ningún prompt interactivo bloqueante en el flujo de fase (el proyecto es agent-agnostic y scriptable por diseño — Principio V; `dialoguer` hoy solo se usa en el menú opcional de `learnkit init`, nunca en el pipeline de sesión). En su lugar, "preguntar al usuario" se traduce a un estado consultable + un comando explícito para resolverlo, exactamente el mismo patrón que ya usa el override de validación semántica.
- **Alternatives considered**: prompt interactivo TTY dentro de `learnkit run analyse`/`learnkit analyse` — se descarta porque rompería el uso no interactivo/scriptado (CI, agentes) que el resto del CLI ya garantiza, y porque el usuario real de este flujo es a menudo el propio agente actuando en nombre de la persona, no una terminal interactiva.

## 4. Dónde vive la lógica de dedup de `consolidate` (FR-010/011, confirmado en `/speckit-clarify`: acotado a vocabulario)

- **Decision**: `learnkit-workflow` (crate del que dependen `analyse`/`consolidate`) NO añade una dependencia de compilación hacia `learnkit-profile` — hoy no la tiene (`crates/learnkit-workflow/Cargo.toml` solo depende de `learnkit-core`/`learnkit-store`) y no se introduce aquí. `learnkit-workflow::consolidate` solo sabe generar y persistir `ConsolidatedCandidate`s genéricos (texto candidato + trazabilidad + un campo `already_exists: bool` que recibe ya calculado). La comprobación de dedup real contra `VocabularyEntry` (por `lemma`, feature 002) la hace el handler CLI (`crates/learnkit-cli/src/commands/consolidate.rs`), que sí depende tanto de `learnkit-workflow` como de `learnkit-profile` (como ya hace hoy `commands/learn.rs`), y le pasa a `learnkit-workflow` el resultado ya resuelto.
- **Rationale**: mantiene `learnkit-workflow` genérico de verdad (Principio VI) — nunca importa ni conoce el concepto de "lema"/idioma, ni siquiera transitivamente vía `Cargo.toml`. El patrón de "el handler CLI orquesta entre crates de dominio" ya es el que usa `commands/cards.rs` (orquesta `learnkit-cards` + `learnkit-media` + `learnkit-profile` juntos) — no es un patrón nuevo.
- **Alternatives considered**: añadir `learnkit-profile` como dependencia de `learnkit-workflow` para que `consolidate.rs` llame directamente al dedup — se descarta porque contaminaría un crate core con una dependencia de un crate de perfil, aunque el propio código de `learnkit-workflow` no llegara a mencionar "lema"; la regla de Principio VI se interpreta aquí de forma estricta (ni la dependencia de compilación debería apuntar de core a perfil).

## 5. Idempotencia de `analyse`/`consolidate` (FR-009)

- **Decision**: mismo patrón que `cards build --force` (feature 002, FR-017f): al ejecutar/confirmar un elemento, si ya existe un `ChecklistItemManifest` con estado `Done` y el `input_fingerprint` coincide con las fuentes actuales, el comando de confirmación es un no-op (informa que ya estaba hecho) salvo que se pase `--force`.
- **Rationale**: reutiliza un patrón ya implementado y probado en este mismo repo en vez de diseñar uno nuevo; consistencia de UX entre comandos.
- **Alternatives considered**: ninguna — es la extensión directa de un patrón ya decidido y validado con uso real.

## Resultado

Todos los desconocidos del Technical Context quedan resueltos. La decisión de mayor impacto para el usuario ya fue confirmada explícitamente en `/speckit-clarify` (§2: redacción delegada al agente). La segunda decisión más relevante para quien lea el código (§4: `learnkit-workflow` nunca depende de `learnkit-profile`, la orquestación cruzada vive en `learnkit-cli`) se señala aquí porque afecta directamente a la estructura de `tasks.md` que generará `/speckit-tasks`.
